# 图灵实验室：项目总览与团队交接

## 1. 项目定位

图灵实验室是一个支持多人同时参与的在线图灵测试主持平台。核心场景是在同一比赛房间内组织人类参赛者、AI 参赛者和独立裁判，通过多轮提问与回答，让裁判根据匿名回答判断每个参赛者的真实身份。

项目不仅包含比赛页面，还包括：

- 用户注册、UID 登录和管理员账号管理；
- 房间创建、邀请码加入、房间所有者权限；
- 真人裁判独立登录、自助入房及多裁判并行判断；
- AI 参赛者和 AI 裁判的手动转录模式；
- OpenAI Chat Completions 兼容模型 API 接入；
- 多轮问题、回答、追问建议、统一揭晓；
- 匿名裁判包快照、单轮和整场 Log；
- WebSocket 实时同步、输入状态提示；
- 完赛房间复用、清空比赛记录和删除房间。

项目的目标是让一场比赛能够由多个房间参与者和多个独立裁判协作完成，同时保留裁判判断隔离和参赛者匿名机制。

## 3. 技术架构

当前实现是单体式 Web 应用，不是前后端分离的多服务架构。

~~~text
浏览器
  |
  | HTTP / JSON
  | WebSocket
  v
FastAPI 应用（app.py）
  |-- 认证、权限与 CSRF
  |-- 房间、轮次、参赛者与裁判业务
  |-- SQLite 数据读写
  |-- WebSocket 房间广播
  |
  +---- model_api.py
  |       |-- HTTPS / OpenAI Chat Completions 兼容请求
  |       |-- Fernet API Key 加解密
  |       |-- DNS 公网地址校验与连接固定
  |
  +---- SQLite 数据库
          |-- 用户与会话
          |-- 房间与参赛者
          |-- 轮次、问题、回答
          |-- 真人 / AI 裁判及判决
          |-- 模型配置、修订记录、裁判包

部署入口：railway_start.py
生产镜像：Dockerfile
部署配置：railway.json
静态前端：static/
~~~

### 技术组成

| 层 | 当前实现 |
|---|---|
| 前端 | 原生 HTML、CSS、JavaScript；无 React/Vue 等前端框架 |
| 后端 | Python、FastAPI、Pydantic |
| 数据库 | SQLite；连接启用外键约束、20 秒 busy timeout 和 WAL |
| 实时通信 | FastAPI WebSocket；房间广播由进程内 Hub 管理 |
| 模型接入 | httpcore、Fernet；OpenAI Chat Completions 兼容协议 |
| 容器 | Docker；生产镜像基于 python:3.12-slim |
| 云部署 | Railway；当前配置为单副本、单 Uvicorn worker |

## 5. 用户角色

### 全站管理员（admin）

- 管理所有房间；
- 管理用户账号、重置密码和删除账号；
- 可以作为房间管理者；
- **不能作为独立真人裁判加入房间**。

### 房主（owner）

- 创建房间的用户；
- 管理自己创建的房间；
- 可以添加 AI 参赛位、AI 裁判和模型配置；
- 可以推进比赛、生成裁判包、锁定传统单裁判模式的结论并揭晓；
- 可以作为本房间参赛者加入；
- **不能同时作为自己房间的独立真人裁判**。

### 人类参赛者（player）

- 通过邀请码以参赛者身份加入；
- 获得匿名代号；
- 提交每轮回答；
- 在作答期间查看其他人类参赛者的输入状态；
- 可向主持人提交问题或追问建议；
- 不能读取尚未统一揭晓的其他参赛者回答。

### 真人裁判（human judge）

- 使用独立账号登录；
- 通过邀请码并明确选择“真人裁判”身份加入；
- 不占参赛者名额；
- 只能看到匿名代号、裁判问题和已经统一揭晓的回答；
- 每轮最多提交一次问题；
- 所有轮次结束后独立锁定自己的最终判断；
- 无法读取其他裁判的判决；
- 同一账号同一时间只能在一个未完赛房间担任真人裁判。

### AI 参赛者（AI player）

- 由房主添加；
- 可以使用手动转录模式，也可以绑定模型配置自动生成回答；
- 使用匿名代号参与统一提交与揭晓；
- 模型调用只读取该 AI 自己此前已完成轮次的回答，不读取其他参赛者的未揭晓回答。

### AI 裁判（AI judge）

- 由房主添加；
- 可以使用手动转录模式，也可以绑定模型配置；
- 可以逐轮提出问题；
- 所有轮次结束后独立锁定最终判断；
- 模型模式下，AI 裁判读取匿名比赛资料，不读取真实身份或其他裁判判决。

## 6. 核心业务流程

1. 用户注册并获得 UID，或使用已有 UID 登录。
2. 用户创建房间成为房主，或者通过邀请码加入已有房间。
3. 加入者选择参赛者或真人裁判身份；管理员账号不显示真人裁判选项，后端也会拒绝该身份。
4. 房主配置人类 / AI 参赛者及真人 / AI 裁判。
5. 裁判提交本轮问题，房主确认并统一开放作答。
6. 参赛者提交回答；服务端在所有在场参赛者提交后统一公开。
7. 重复进行多轮；必要时生成匿名裁判包。
8. 所有轮次完成后，各独立裁判分别锁定最终判断。
9. 房主确认所有独立裁判均已锁定，再揭晓真实身份和结果。
10. 完赛后可下载整场 Log、复用房间、清空记录或删除房间。

## 7. 关键业务限制

| 项目 | 当前限制 |
|---|---|
| 在场参赛者 | 最多 8 人，包含人类和 AI 参赛位 |
| 比赛轮数 | 最多 100 轮 |
| 裁判席 | 每房间最多 12 位，包含真人和 AI 裁判 |
| 每轮人类裁判问题 | 每位真人裁判每轮最多提交一次 |
| 每轮 AI 裁判问题 | 每个 AI 裁判席每轮最多提交一次 |
| 人类裁判跨房间占用 | 同一 UID 不能同时担任两个未完赛房间的真人裁判 |
| 人类裁判与参赛者身份 | 同一账号不能在同一房间同时担任裁判和参赛者 |
| 回答揭晓 | 当前在场参赛者全部提交后统一揭晓 |
| 最终揭晓 | 所有独立裁判均锁定判断后才能揭晓 |

具体约束以 app.py 中的校验为准。

## 8. 重要安全与隐私边界

- 所有需要登录的房间数据接口都会先验证会话和房间权限。
- 写请求校验 Origin 和 CSRF Token。
- 浏览器对房间写请求附带当前 match_number，降低旧页面误写新比赛的风险。
- 未完成统一提交前，普通参赛者和裁判都不能读取其他参赛者的回答正文。
- 真人裁判视图只返回匿名代号，不返回参赛者真实姓名、UID 或账号信息。
- 裁判视图只返回自己的判决，不返回其他裁判判决。
- 跨房间裁判冲突提示按查看权限区分：无权查看冲突房间的人只会收到通用提示，不会获得对方房间标题或编号。
- API Key 使用 Fernet 加密存入 SQLite，浏览器只收到是否已保存的状态。
- 模型 API Base URL 只允许 HTTPS 公网地址；模型请求使用已校验的 DNS 地址连接，并保留原始域名的 TLS 校验。

## 10. 关键协作原则

- 先理解权限和匿名规则，再修改房间接口。
- 不要只改前端隐藏按钮；所有权限必须由后端验证。
- 修改数据库结构时，考虑已有线上 SQLite 数据和备份恢复路径。
- 涉及裁判隔离、统一揭晓、房间复用或删除时，必须补充回归测试。
- 不要把“当前 UI 没有入口”误认为“后端接口不存在”；PR #8 移除了旧的真人裁判创建/绑定表单，但对应旧 API 路由仍在 app.py 中。
