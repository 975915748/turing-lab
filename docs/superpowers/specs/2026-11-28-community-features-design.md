# 好友邀房、公开大厅与出题灵感库设计

- 日期：2026-11-28
- 状态：待实施
- 适用基线：仓库 main 当前代码
- 范围：产品优先级清单中的 1、3、4
  1. 好友一键邀房
  2. 公开大厅房间列表
  3. 公共出题灵感库

本文是实现规格，不代表功能已经开发或部署。

## 1. 目标与非目标

### 1.1 目标

- 让房主不再依赖站外复制邀请码即可邀请现有好友进入房间。
- 让用户能够在大厅发现并加入主动公开、仍允许加入的房间。
- 给真人裁判提供可检索、可随机抽取、可编辑的出题灵感，降低出题门槛。
- 复用当前账号、好友、房间、角色准入、WebSocket 和 SQLite 事务机制，避免另起一套身份或比赛规则。
- 私密房间继续保持私密；现有邀请码加入流程保持兼容。

### 1.2 本批明确不做

- 不开发赛后战报、历史比赛归档或分享长图。
- 不开发观战席、观众竞猜、裁判积分、好友榜或全站榜。
- 不开发浏览器桌面通知、推送权限或提示音。
- 不开放用户投稿、审核、点赞、收藏和题库排行榜；本批题库为项目内置内容。
- 不改变现有比赛判定、匿名规则、单轮工作流、模型 API 或人设冻结逻辑。
- 不调整当前参赛者上限 8 人、裁判上限 12 人。
- 不公开房间邀请码、模型 API 配置、API Key、System Prompt、未公开问题或回答。

## 2. 当前代码基线与约束

以下是设计时应保留的现有行为：

1. 房间创建、邀请码加入、比赛状态和角色权限主要位于 app.py。现有邀请码入口为 POST /api/join。
2. 当前参赛者上限由 MAX_PLAYERS = 8 控制，真人 / AI 裁判上限由 MAX_JUDGES = 12 控制。
3. 参赛者准入依赖 active_participant_count、ensure_roster_unlocked 等检查；真人裁判准入依赖 check_judge_registration、check_no_other_active_judge_room 等检查。新入口应复用共享角色互斥、容量判断和席位写入逻辑，但不能把不同入口的准入策略合并成一个“最严格”检查；必须保留邀请码加入的既有行为，具体见 2.1。
4. 首轮开始后，rooms.match_started_at 会记录开赛状态；开赛后不允许正常增加参赛者。人设冻结、问题已提交、裁判判决锁定等状态也会限制名单变更。
5. 好友、好友备注、私信及账号级 WebSocket 位于 social.py。账号 WebSocket 路径为 /ws/messages，服务端通过 hub.notify_account 推送事件。
6. 当前前端为 static/app.js 的原生 JavaScript 事件委托结构；大厅由 renderLobby() 生成，好友数据通过 /api/me/social 获取。
7. 真人独立裁判的问题入口为 POST /api/rooms/{room_id}/judge-questions；房主旧版手工问题入口为 POST /api/rooms/{room_id}/question。旧版 /api/rooms/{room_id}/suggestions 已返回 410，不得复活为题库接口。
8. 独立真人裁判在本轮尚未开始、且本人尚未提交问题时，才显示 judge-question 表单。AI 裁判代录入口用于忠实转录 AI 输出，不应被题库内容替代。
9. app.py 的 init_db() 与 social.py 的 ensure_app_schema() 负责现有 SQLite 表和增量迁移。新增字段和表必须采用可重复执行、保留旧数据的迁移方式。
10. 本项目采用 SQLite 和单进程工作流执行模型。新增写操作应使用现有 connection(immediate=True) 事务习惯，不引入多 worker 假设。

### 2.1 加入行为兼容矩阵（必须先读）

共享加入逻辑只统一“角色互斥、已有席位识别、人数上限、成员 / 裁判席写入、事件记录”等共同操作；入口特有的资格判断必须留在各自的策略层。不得为了抽取函数而改变现有邀请码加入语义。

当前 `POST /api/join` 的实际顺序和行为如下，重构后必须保持：

- 房间关闭时拒绝加入。
- 真人裁判：先处理已在本场退出的裁判限制；管理员不能作为独立真人裁判；若账号已经是本房间裁判，先幂等返回，不再执行新裁判准入检查；新裁判才调用 `check_judge_registration`，保留其人设冻结、房间状态、房主身份、管理员、参赛者 / 裁判互斥、跨房间任职和 `MAX_JUDGES` 检查。
- 参赛者：本房间裁判不能改作参赛者；已存在且未退出的成员先幂等返回，不执行名单锁定检查；主动退赛者仅在 `leave_reason='voluntary'` 且本场尚未开始时允许重入，被移除者不能重入本场；新增 / 重入调用 `ensure_roster_unlocked(..., allow_frozen=True)`；主动退赛重入时另检查 `active_participant_count`，新成员通过 `new_alias` 的容量检查后写入。
- `allow_frozen=True` 是当前邀请码参赛者加入的既有兼容行为：它允许在 AI 人设配置冻结但其他名单条件仍满足时加入；它不会放宽房间关闭、首轮已开始或首轮问题已提交等其他检查。
- `POST /api/register` 的邀请码注册是另一条既有入口；本次若触及该路径，也必须单独记录并保持原行为，不得默认为其套用新入口策略。

新邀请接受和公开加入使用独立的 `validate_discovery_join` 资格检查：

1. 房间必须 open，`match_started_at IS NULL`，首轮仍为 draft，首轮主持人问题和独立裁判问题均未提交，且没有锁定裁判结论。
2. 对尚未拥有目标角色的新增参赛者，必须调用 `ensure_roster_unlocked(..., allow_frozen=False)`；因此人设冻结会阻止通过邀请或公开大厅新增参赛者。已有同角色席位的幂等返回不应被容量检查或重复写入阻断。
3. 新增真人裁判继续调用 `check_judge_registration`；已有本房间真人裁判按现有顺序幂等返回。
4. 通过来源策略检查后，再调用共享加入核心执行角色互斥、容量、退赛 / 重入规则和席位写入。邀请接受还必须在同一事务内更新邀请状态。
5. `POST /api/join` 不得调用 `validate_discovery_join`，不得把 `allow_frozen=True` 改为默认值或 `False`，也不得把“已有成员先返回”的顺序移到名单锁定检查之后。

共享函数可以接收显式来源策略或由调用方先完成策略检查，但不得在函数内部偷偷采用所有入口中最严格的限制。对旧邀请码路径、新邀请路径和公开加入路径分别编写行为回归测试。

## 3. 功能 A：好友一键邀房

### 3.1 用户流程

1. 房主或全站管理员进入自己有管理权限的房间。
2. 房间尚未开赛且名单仍允许变更时，显示“邀请好友”入口。
3. 打开好友选择面板，展示当前账号的好友备注、显示名和 UID。
4. 用户选择一名或多名好友，并选择本批邀请身份：参赛者或真人裁判。
5. 服务端逐个验证好友关系和邀请权限，创建邀请记录。
6. 被邀请者收到站内实时通知；在大厅邀请列表中看到邀请来源、房间名、身份和有效期。
7. 被邀请者接受后，服务端在同一事务中重新验证房间状态与角色准入，并直接加入房间。前端随后打开该房间，不要求输入邀请码。
8. 被邀请者可以拒绝；邀请发送者可以撤回仍待处理的邀请。
9. 房间开赛或关闭时，该房间所有待处理邀请失效。邀请过期后也不能接受。

### 3.2 邀请权限与准入规则

发送邀请：
- 必须登录并通过现有 Origin、CSRF 校验。
- 发送者必须是该房间房主或全站管理员，即通过现有 require_room_manager 校验。
- 接收者必须是发送者当前好友，且账号未删除。
- 房间必须为 open，尚未开始首轮，且名单仍可变更。
- 每个房间、每个接收者最多保留一条 pending 邀请。重复发送相同身份的邀请返回已有待处理记录；若身份不同，要求先撤回旧邀请。
- 单次请求最多处理 20 个 UID；单个目标失败不应导致其他有效目标的邀请丢失，响应应逐个返回 sent / skipped 结果。
- 发送邀请时不向发送者泄露接收者在其他房间的具体任职信息。角色冲突在接受时由服务端判断。

接受邀请：
- 只有被邀请账号本人可以接受或拒绝。
- 接受时必须确认邀请仍为 pending、未过期、双方仍是好友、房间仍可加入。
- 邀请接受必须先通过 `validate_discovery_join`：房间 open、首轮未开始、首轮问题未提交、裁判结论未锁定。
- 新增参赛者使用 `ensure_roster_unlocked(..., allow_frozen=False)`，不能通过邀请绕过人设冻结；若接收者已经是本房间同角色有效成员，则走共享核心的幂等返回，不重复检查容量或写入席位。
- 新增真人裁判调用现有 `check_judge_registration`，包含管理员账号限制、房主不能担任本房间裁判、参赛者与裁判互斥、MAX_JUDGES 上限，以及同一账号不能同时在其他未完赛房间担任真人裁判的限制；已有本房间裁判先幂等返回。
- 上述限制属于邀请入口策略，不得反向修改 `POST /api/join` 的 `allow_frozen=True` 和既有检查顺序；详见 2.1。
- 所有校验、加入成员 / 裁判席、邀请状态更新必须在一个 SQLite immediate transaction 内完成，避免满员竞争或重复点击造成重复加入。
- 接受失败时返回明确的可理解原因，例如“房间已开赛”“参赛者名额已满”“你正在其他未完赛房间担任真人裁判”。不得返回其他房间的名称或敏感信息。
- 已接受的邀请重复提交应幂等：若接收者仍是本房间对应角色，返回已加入结果；不得重复插入成员或裁判记录。

### 3.3 邀请状态与有效期

状态仅允许：
- pending：等待接收者处理。
- accepted：已接受并成功加入。
- rejected：接收者拒绝。
- cancelled：发送者撤回，或房间开赛 / 关闭、好友关系解除、账号删除等原因使邀请失效。
- expired：超过有效期。

默认有效期为创建后 30 分钟，使用服务端 UTC 时间计算。该值先作为常量，不增加用户可配置项。

失效规则：
- 首轮正式开局或房间关闭时，将该房间所有 pending 邀请更新为 cancelled。
- 好友关系被任意一方删除时，双方之间尚未处理的邀请更新为 cancelled。
- 账号软删除时，涉及该账号的 pending 邀请更新为 cancelled。
- 到期邀请在列表读取或接受时惰性更新为 expired；本批不增加后台定时任务。
- **重新发送邀请时也必须先清理过期记录：**在创建邀请的同一个 `immediate` 事务内，先将该 `room_id + invitee_user_id` 下 `status='pending' AND expires_at <= now` 的记录更新为 `expired`，再查询是否存在有效 pending 邀请，最后决定复用、提示先撤回或插入新记录。不得只依赖接收者先打开邀请列表来释放部分唯一索引。
- 关闭后重新开赛属于新场次；旧邀请不恢复，必须重新邀请。

### 3.4 数据库设计

在 social.py 的 ensure_app_schema() 中新增 room_invites 表，字段建议如下：

| 字段 | 类型 / 约束 | 说明 |
|---|---|---|
| id | INTEGER PRIMARY KEY AUTOINCREMENT | 邀请 ID |
| room_id | INTEGER NOT NULL REFERENCES rooms(id) ON DELETE CASCADE | 房间 |
| inviter_user_id | INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE | 邀请发送者 |
| invitee_user_id | INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE | 被邀请者 |
| role | TEXT NOT NULL CHECK role IN ('player','judge') | 受邀身份 |
| status | TEXT NOT NULL CHECK | pending / accepted / rejected / cancelled / expired |
| created_at | TEXT NOT NULL | 创建时间 |
| expires_at | TEXT NOT NULL | 到期时间 |
| responded_at | TEXT NULL | 接受或拒绝时间 |
| updated_at | TEXT NOT NULL | 最近更新时间 |

增加索引：
- 接收者待处理邀请：invitee_user_id、status、created_at。
- 发送者待处理邀请：inviter_user_id、status、created_at。
- 房间待处理邀请：room_id、status。
- 部分唯一索引：同一 room_id、invitee_user_id 只能有一条 status='pending' 的记录。

不要把结构化邀请写进 dm_messages.text。私信仍保持纯文本语义，邀请卡片是独立业务记录。

### 3.5 API 设计

| 方法与路径 | 权限 | 用途 |
|---|---|---|
| GET /api/me/room-invites | 登录用户 | 返回当前账号收到和发出的 pending 邀请；读取时清理过期记录 |
| POST /api/rooms/{room_id}/invites | 房主 / 管理员 | 批量邀请好友，body 包含 uids 和 role |
| POST /api/room-invites/{invite_id}/accept | 被邀请者 | 接受并直接加入 |
| POST /api/room-invites/{invite_id}/reject | 被邀请者 | 拒绝邀请 |
| POST /api/room-invites/{invite_id}/cancel | 发送者；房主 / 管理员可撤回本房间邀请 | 撤回邀请 |

批量邀请请求示例字段：
- uids：字符串数组，1～20 个 UID，不接受重复 UID。
- role：player 或 judge，本批所有目标使用相同身份。

批量响应应逐个返回目标 UID、invite_id（成功时）、状态和失败原因。不得因单个目标不满足好友关系而回滚其他目标的成功邀请。

### 3.6 WebSocket 与前端通知

- 复用 /ws/messages 和 hub.notify_account，不把邀请写入聊天记录。
- 增加 room_invite_created、room_invite_updated 事件；事件只携带邀请 ID 和必要的刷新提示，不携带邀请码、CSRF、模型配置或完整好友数据。
- 复用 `/ws/messages`，但必须把**账号 socket 的生命周期**与**个人中心 / 私信 UI 状态**分开。账号 socket 在登录会话内持续连接大厅、房间和个人中心；`clearDmState()` 只清理当前私信会话数据，不得关闭账号 socket。只有退出登录、账号 / CSRF 会话变化或会话失效时，才由独立的 `stopAccountSocket()` 关闭连接。
- socket 连接、重连、事件处理和异步刷新必须捕获并复核 UID、CSRF、账号 epoch、socket 实例；旧账号迟到事件不得更新新账号状态。
- 登录成功和 socket 每次重连后，必须主动拉取 `/api/me/room-invites` 补回离线期间错过的邀请事件；同时刷新好友 / 未读摘要。不能把 WebSocket 推送当作唯一数据来源。
- 邀请、私信、锁名事件只更新对应状态或局部区域。处于大厅或比赛页面时，不得调用 `renderPersonalCenter()` 把当前页面替换成个人中心；仅当个人中心确实处于前台时才刷新其社交面板。
- `dm_message` 只有在用户实际打开对应私信会话（个人中心可见且当前选中的 `dmUid` 与发送者一致）时才追加到可见会话并标记已读。未打开该会话时只刷新未读摘要，不得因为 socket 收到消息或后台保留了 `dmUid` 就标记已读。
- 大厅显示待处理邀请数量和邀请列表；房间内收到新邀请时显示轻量提示，并提供“去大厅查看”入口。
- **“去大厅查看”不是无副作用导航：**必须调用现有 `leaveCurrentRoom()` 退房流程，不得直接调用 `loadLobby()`、直接改 hash 或直接清空 `roomId`。按钮文案须明确提示“前往大厅将退出当前房间”。普通成员确认后退出并释放本房间身份；房主处于 open 房间时必须先显示现有关闭确认，确认后才关闭房间并返回大厅，取消则留在原房间。邀请列表只能在退房流程成功后显示。
- 接受后跳转到返回的 room_id；拒绝或撤回后刷新邀请列表。
- 退出登录、切换账号时关闭旧账号 socket、清空邀请状态和未完成请求；大厅 / 房间 / 个人中心之间切换不得关闭账号 socket。

## 4. 功能 B：公开大厅房间列表

### 4.1 产品规则

- 创建房间时增加“公开在大厅展示”开关，默认关闭。
- 可填写可选房间说明，最多 160 个字符；只有开启公开展示时才对大厅用户返回。
- 房主 / 管理员可以在首轮开赛前修改公开状态和说明。
- 首轮正式开始后自动从公开列表移除；不允许在本场比赛开始后重新公开。
- 私密邀请码加入功能完全保留。公开房间也继续保留邀请码，房主仍可站外分享。
- 房间完成或关闭后不出现在公开列表。
- 房间再次开赛会清空上一场比赛记录并重置首轮状态；如果房间公开开关仍开启，新场次重新满足准入条件时可以再次出现在大厅。
- 本批不开放自定义参赛者人数上限，继续使用 MAX_PLAYERS=8 和 MAX_JUDGES=12。

### 4.2 公开列表的严格准入条件

公开列表只返回同时满足以下条件的房间：
- public_listing = 1。
- rooms.status = 'open'。
- match_started_at IS NULL。
- verdict_locked_at IS NULL。
- 当前仍处于首轮 draft。
- 首轮没有已提交的主持人问题或独立裁判问题。
- 本场名单尚未冻结。
- 对当前浏览者至少存在一种可用加入身份。

最后一项按浏览者分别计算：
- can_join_player：未与本房间现有裁判身份冲突，名单仍可修改，且现有参赛者 + AI 参赛席未达到 8 人。
- can_join_judge：浏览者不是管理员、不是房主、不是本房间参赛者；没有其他未完赛房间的真人裁判任职；当前裁判席未达到 12 人，且裁判配置仍允许加入。
- 如果当前浏览者两种身份都不能加入，该房间不必出现在其公开列表中。

公开列表是发现入口，不是准入授权。点击加入时必须在服务端重新执行完整校验。

### 4.3 大厅展示字段

每个公开房间只返回：
- room_id、title、public_description。
- owner_display_name：房主公开显示名；不公开 owner UID。
- player_count、max_players。
- human_judge_count、ai_judge_count、max_judges。
- round_duration_seconds。
- ai_player_count、是否存在绑定模型的 AI 席位。
- tags：由服务端根据真实配置生成。
- created_at。
- can_join_player、can_join_judge。

不得返回：
- invite_code。
- 参赛者账号、UID、匿名代号与真实身份映射。
- 房间公共聊天、问题、回答、裁判判决。
- AI 模型配置名、Base URL、API Key、System Prompt、私有模型配置 ID。
- 未揭晓的人设快照或比赛内部状态。

标签由现有配置计算，不单独存储。例如：
- 配置了单轮限时：限时 120s。
- 存在 AI 参赛席：含 AI 参赛席。
- 存在绑定模型的 AI 席位：含模型 AI。
- 有真人独立裁判且没有 AI 裁判：纯真人裁判。
- 有 AI 裁判：含 AI 裁判。

标签是概览，不得暗示房间一定可以加入；最终以 can_join_* 和服务端准入为准。

### 4.4 数据库与迁移

在 rooms 表增加：
- public_listing INTEGER NOT NULL DEFAULT 0。
- public_description TEXT NOT NULL DEFAULT ''。

在 app.py 的 init_db() 中加入 CREATE TABLE 定义和兼容旧库的 ALTER TABLE 增量迁移。旧房间全部默认为私密，不自动公开。迁移可重复执行，不重建 rooms、不清空比赛记录。

### 4.5 API 设计

| 方法与路径 | 权限 | 用途 |
|---|---|---|
| GET /api/public/rooms | 登录用户 | 查询当前浏览者可加入的公开房间 |
| PUT /api/rooms/{room_id}/visibility | 房主 / 管理员 | 设置公开开关与公开说明 |
| POST /api/rooms/{room_id}/join | 登录用户 | 按 player / judge 身份直接加入公开房间 |

GET 查询支持 limit（默认 30，最大 50）和 before_id 游标，按 room_id 倒序分页。响应不包含邀请码。

创建房间 POST /api/rooms 的 RoomData 增加可选 public_listing（默认 false）和 public_description（默认空字符串），旧客户端不传字段时行为不变。

公开加入接口只接受 room_id 和 role，不接受用户传入的 owner_id、member_id、alias 或邀请码。该接口必须确认房间当前仍公开且符合公开准入条件，再调用与邀请码加入共用的内部加入逻辑。

### 4.6 前端交互

大厅增加“公开对局”区域：
- 显示房名、房主昵称、人数、裁判数量、限时、自动标签和房间说明。
- 按 can_join_player / can_join_judge 显示对应加入按钮。
- 加入成功后直接打开房间。
- 提供刷新按钮；本批不要求公共房间列表实时推送。

创建房间表单增加默认关闭的公开开关和说明输入框。房间管理视图在首轮开赛前允许房主修改公开状态。开赛后显示当前公开状态已自动停止展示，不提供重新开启入口。

## 5. 功能 C：公共出题灵感库

### 5.1 定位与首版内容

首版是所有登录用户可用的内置题库，不是允许任意用户写入的公共内容平台。

建议至少提供 24 道经过整理的中文问题，每类不少于 6 道：
- 逻辑陷阱：检查推理步骤、条件理解和自我纠错。
- 中文语境与表达：检查歧义、语用、上下文和自然表达。
- 主观体验与记忆：检查是否会把无法验证的个人经历编造成事实；问题应允许诚实表达限制。
- 多轮追问：提供可以连续追问的起始问题，考察上下文一致性和修正能力。

每条题目包含稳定 ID、分类、标题、正文和可选标签。题目正文不得超过现有真人裁判问题的 3000 字限制。

### 5.2 使用范围

首版只接入独立真人裁判的 judge-question 输入框：
- 当前轮仍为 draft。
- 当前裁判尚未提交本轮问题。
- 该裁判有权提交本轮问题。

不接入 AI 裁判问题代录表单，因为该表单用于忠实转录 AI 的原始输出。
不接入旧版房主 question 表单，因为该表单用于从外部裁判聊天窗口复制原文；不能把题库建议混成外部裁判原话。
不改变现有提交 API、每位真人裁判每轮只能提交一次的规则，以及房主统一开局流程。

### 5.3 交互

- 在真人裁判问题输入框旁增加“出题灵感”按钮。
- 打开面板后可按分类筛选、关键词搜索、随机抽取。
- 列表展示标题、简短分类和题目预览。
- 点击“填入”只把文本放入当前 textarea，不调用提交 API。
- 填入后用户可自由编辑，再通过原有“提交并实时同步问题”按钮提交。
- 如果 textarea 已有非空草稿，替换前必须二次确认；取消后保留原草稿。
- 面板关闭、切换分类或搜索时，不得清空用户已输入内容。
- 题目正文必须通过现有 esc() 等安全方式渲染，不能将题库字符串直接拼入未经转义的 HTML。

### 5.4 数据与 API

新增 question_bank.py，集中保存版本化内置数据和分类元数据；不新增 SQLite 表。当前 Dockerfile 采用逐个列出 Python 模块的 `COPY` 方式，因此必须同步把 `question_bank.py` 加入 Dockerfile 的显式复制列表，否则本地导入成功也可能在生产容器启动时因模块缺失而失败。

新增只读接口：
- GET /api/question-bank
- 可选参数 category、q、limit。
- 仅返回稳定 ID、分类、标题、正文、标签和题库版本。
- 要求登录，但不要求 CSRF，因为没有写操作。
- 不提供新增、修改、删除、投稿或收藏接口。

题库变更通过代码审查和版本提交发布。稳定 ID 不随标题或正文的小幅修改而改变；删除题目时不得把旧 ID 分配给另一道题。

## 6. 共同安全与一致性要求

1. 所有写接口继续使用现有 caller(request, db, mutate=True)，保持 Origin、CSRF 和登录验证。
2. 房间加入、邀请接受和公开加入均由服务端重新检查房间状态、名单锁定、身份互斥和人数上限。前端按钮状态不是安全边界。
3. 邀请接受、成员 / 裁判席写入、邀请状态更新必须处于同一 immediate transaction。
4. 邀请和公开列表不得泄露房间邀请码或内部参赛资料。
5. 所有异步前端响应与 WebSocket 事件必须绑定 UID、CSRF、账号 epoch 和当前 socket；旧会话响应不得覆盖新账号状态。
6. 账号软删除和好友删除必须清理相关 pending 邀请，但不能删除原有私信历史。
7. 所有用户可见文本使用现有规范化、长度限制和 HTML 转义机制。
8. 列表接口必须限制返回数量；邀请发送必须有速率限制，防止骚扰和批量滥用。
9. 题库是只读静态数据，不得把用户填写的草稿、提交的问题或比赛回答回写进题库。
10. 新增表和列必须兼容已有 Railway SQLite 数据库；不允许通过删库重建完成迁移。
11. 新增 Python 模块必须同步更新 Dockerfile 的显式 `COPY` 列表；Docker 验收必须在构建出的容器内执行模块导入检查，不能只在宿主机测试。

## 7. 验收标准

### 7.1 好友邀房

- 非房主 / 非管理员不能替房间发送邀请。
- 非好友、已删除账号和自己不能成为邀请目标。
- 可以一次选择多名好友；有效邀请成功，单个无效目标有独立失败原因。
- 重复发送不会生成多条 pending 邀请；即使旧 pending 已过期且接收者从未打开过邀请列表，重新发送也能在创建事务中先过期旧记录并成功创建新邀请。
- 只有接收者本人可以接受或拒绝，发送者可以撤回。
- 接受玩家邀请会创建且只创建一条成员记录；接受裁判邀请会创建且只创建一条真人裁判记录。
- 参赛者满员、裁判满员、管理员担任真人裁判、房主担任本房间裁判、参赛者与裁判互斥、跨房间裁判冲突均被服务端正确拦截。
- 房间开赛、关闭、邀请到期或好友关系解除后，邀请不能再接受。
- 双击接受、并发接受、旧账号 WebSocket 迟到事件不会造成重复加入或串号。
- 大厅 / 房间 / 个人中心切换不关闭会话级账号 socket；断线重连会主动拉取邀请；社交事件不会重绘当前比赛页面；未打开的私信会话不会被自动标记已读。
- 房间内点击“去大厅查看”时，普通成员会按现有流程退房；房主必须确认关闭；取消确认后仍留在原房间。
- 接受成功后直接打开对应房间，不需要邀请码。

### 7.2 公开大厅

- 新建房间默认不公开；旧数据库升级后所有旧房间仍为私密。
- 只有房主 / 管理员可以在允许阶段修改公开状态。
- 私密、已开赛、已完赛、已关闭、名单已锁定的房间不会出现在公开列表。
- 公开列表只返回安全概览，不包含邀请码、UID、聊天、问题、回答、判决和模型凭据。
- 参赛者或裁判加入都走公开入口专用资格检查和共享加入核心；满员、锁名、人设冻结和角色冲突不会被绕过，同时不得改变邀请码入口现有 `allow_frozen=True`、已有成员幂等返回和主动退赛重入行为。
- 开赛后房间从列表消失；再次开赛时按保留的公开开关重新判断。
- 分页、搜索参数和数量上限经过测试。

### 7.3 出题灵感库

- 分类、搜索和随机抽取结果稳定且只读。
- 只有可提交问题的真人裁判能看到题库入口。
- 题库内容填入输入框后仍可编辑；填入动作不会自动提交。
- 替换非空草稿需要确认；取消确认不会丢失原草稿。
- AI 裁判原文代录和外部裁判转录入口不被题库污染。
- 题库正文转义安全，长度满足提交接口限制。
- 题库接口不写入数据库、不修改比赛记录。
- Dockerfile 显式复制 `question_bank.py`；构建后的容器可成功执行 `python -c "import question_bank"`，并能启动应用、访问只读题库接口。

## 8. 实施顺序与依赖

1. 先梳理并测试邀请码加入兼容矩阵，再抽取只共享角色互斥、容量、席位写入的内部核心；入口特有资格检查分开保留，保证邀请码加入现有行为不变。
2. 实现好友邀请表、接口、账号级 WebSocket 事件和大厅 / 房间通知 UI。
3. 在 rooms 上增加公开字段、迁移、公开列表 API、可见性设置和公开加入 UI；公开加入复用第 1 步的共享函数。
4. 实现只读题库数据、查询 API 和真人裁判输入框集成。
5. 完成后端、浏览器、旧功能回归、Docker 镜像构建和容器内模块导入验收，再提交独立 PR。

每个阶段都应保持可单独回归；不得为赶进度删减既有好友私信、账号切换保护、房间加入或比赛工作流测试。
