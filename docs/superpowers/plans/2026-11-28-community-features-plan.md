# 好友邀房、公开大厅与出题灵感库实施计划

> 执行依据：docs/superpowers/specs/2026-11-28-community-features-design.md  
> 目标：实现好友一键邀房、公开大厅房间列表和内置出题灵感库。  
> 基线：main 当前代码。  
> 技术栈：FastAPI、SQLite、原生 JavaScript、pytest、Playwright。  
> 本计划只描述后续实施步骤；实施时应在独立功能分支上完成，不直接修改 main，不部署生产环境。

## 全局约束

- 先阅读并遵循设计规格；遇到代码与规格不一致时，先查清现有行为，不得直接绕过权限检查。
- 保留邀请码加入流程、好友关系、私信、账号级 WebSocket、名字锁定、角色互斥和比赛工作流。
- 共享加入逻辑只统一角色互斥、已有席位幂等识别、人数上限、席位写入和事件记录；各入口自己的资格检查必须分开，禁止将最严格策略套到所有来源。
- 必须保留现有 `POST /api/join` 的 `ensure_roster_unlocked(..., allow_frozen=True)`、已有成员提前幂等返回、主动退赛重入条件和裁判检查顺序；邀请 / 公开入口的额外限制只作用于这两个新入口。
- 新增 `question_bank.py` 必须同步加入 Dockerfile 的显式 `COPY` 列表，并在构建后的容器内验证模块导入。
- 旧房间默认私密；新增字段迁移不得重建或清空 SQLite 数据。
- 公开列表不得返回邀请码、UID、私聊、题目答案、裁判判断或模型凭据。
- 题库只读；不恢复已停用的 suggestions API。
- 不实现赛后战报、观战席、积分榜、桌面通知、用户投稿或题库收藏。
- 异步前端响应必须校验 UID、CSRF、账号 epoch 和当前 socket，防止账号切换串号。
- 不改生产数据、密钥、Railway 配置或部署状态。

## 阶段 1：抽取共享房间加入逻辑

**目标：** 邀请接受和公开加入复用席位写入核心，但不改变旧邀请码加入的来源策略。

- [ ] 先为当前 `POST /api/join` 编写兼容测试，逐项固定现有行为：房间关闭拒绝；已存在真人裁判 / 参赛者提前幂等返回；真人裁判新加入调用 `check_judge_registration`；参赛者新加入 / 重入使用 `ensure_roster_unlocked(..., allow_frozen=True)`；主动退赛重入只允许 `leave_reason='voluntary'` 且本场未开始；容量与角色互斥保持原状。
- [ ] 为 `room_id + user + role` 抽取内部共享加入核心，只负责角色互斥、已有席位识别、容量检查、成员 / 裁判席写入、重入记录和事件记录；不要把所有来源的资格检查硬塞进该核心。
- [ ] 将邀请码入口接入共享核心时，保留原有检查顺序和 `allow_frozen=True`，不得把默认 `False` 或新入口的严格限制反向套用到邀请码路径。
- [ ] 邀请和公开加入分别先执行 `validate_discovery_join`：房间 open、未开始首轮、首轮问题未提交、裁判结论未锁定；新参赛者额外调用 `ensure_roster_unlocked(..., allow_frozen=False)`，新真人裁判调用 `check_judge_registration`。已有同角色有效席位应幂等返回，不重复计数或写入。
- [ ] `POST /api/register` 的邀请码注册若被重构触及，必须保留其原有 `allow_frozen=True` 行为和注册事务；否则不必为本次抽取而改动该入口。
- [ ] 新增或补充后端测试，分别覆盖旧邀请码、好友邀请、公开加入三条路径：人设冻结时的差异、已存在席位的幂等顺序、满员、锁名、主动退赛重入、角色互斥、裁判跨房间冲突和房间关闭。
- [ ] 确认旧邀请码路径请求 / 响应兼容，且行为测试证明本阶段没有改变既有规则。

## 阶段 2：好友一键邀房

### 数据层与接口

- [ ] 在 social.py 的 ensure_app_schema() 新增 room_invites 表、状态 CHECK、查询索引和 pending 部分唯一索引。
- [ ] 迁移必须幂等，旧好友、私信、积分数据保持不变。
- [ ] 新增 GET /api/me/room-invites，返回当前用户收到和发出的待处理邀请，并惰性更新过期记录。
- [ ] 新增 POST /api/rooms/{room_id}/invites，校验房间管理权限、好友关系、账号状态、请求数量和速率限制。
- [ ] 单次最多 20 个目标；逐个返回成功 / 跳过结果，不能因单个无效目标丢失其他成功邀请。
- [ ] 新增 accept、reject、cancel 接口，所有写操作执行 Origin、CSRF 和当前用户权限检查。
- [ ] accept 使用 immediate transaction：重读邀请、检查有效期和好友关系、调用共享加入函数、更新邀请状态。
- [ ] accept 对已成功加入的重复请求幂等；失败时不留下半完成的成员记录。
- [ ] 在房间开赛和关闭的状态转换中取消待处理邀请；好友删除、账号软删除时取消相关邀请。
- [ ] 到期邀请在列表读取或接受时更新为 expired，不增加后台定时任务。
- [ ] 创建新邀请时，在同一个 `immediate` 事务内先把当前 `room_id + invitee_user_id` 的过期 pending 更新为 expired，再查询有效 pending / 执行唯一约束检查 / 插入新记录；不得因旧过期记录仍占用部分唯一索引而返回过期邀请。
- [ ] 新增回归：不先 GET 邀请列表，等待旧邀请过期后直接重新发送，必须创建新的 pending 邀请；并发重复发送仍只能留下一个有效 pending。

### WebSocket 与前端

- [ ] 扩展 /ws/messages 的事件类型，增加 room_invite_created 和 room_invite_updated。
- [ ] 将 `/ws/messages` 调整为登录会话级账号 socket：大厅、房间、个人中心切换时连接保持不变；退出登录、账号 / CSRF 会话变化时才关闭。
- [ ] 将 `clearDmState()` 限定为清理私信面板与草稿状态，不再关闭账号 socket；新增独立 `stopAccountSocket()` 管理连接生命周期。
- [ ] 检查 `clearPersonalModelState()` 的调用点：只有登出、账号 / CSRF 会话变化或会话失效才停止账号 socket；大厅 / 房间 / 个人中心导航不能借由状态清理间接断开它。
- [ ] 登录成功和每次 socket 重连后主动拉取 `/api/me/room-invites`，并刷新好友 / 未读摘要，补回离线期间错过的通知。
- [ ] socket 建立、重连、消息处理和异步刷新均核对 UID、CSRF、账号 epoch、socket 实例。
- [ ] 大厅增加待处理邀请角标和邀请列表，展示房间名、邀请人、受邀身份和剩余有效期。
- [ ] 房间管理视图在名单可变更时增加“邀请好友”按钮。
- [ ] 好友选择面板支持多选和本批统一身份；无好友时提供前往个人中心的入口。
- [ ] 接收者可接受 / 拒绝；发送者可撤回；接受成功后直接打开房间。
- [ ] 当前处于房间时收到邀请，显示轻量通知和“去大厅查看”入口，不强制切换当前比赛。
- [ ] “去大厅查看”按钮明确标注会退出当前房间，并调用现有 `leaveCurrentRoom()`；不得直接 `loadLobby()` 或仅改 hash。
- [ ] 普通成员确认后按现有流程退房并释放身份；房主返回大厅前必须确认关闭房间，取消确认后保持原房间页面和连接不变。
- [ ] 退出登录、切换账号和 socket 断开时清理邀请状态与旧请求。

## 阶段 4：内置出题灵感库

- [ ] 新增 question_bank.py，集中保存版本号、分类和至少 24 条内置题目。

- [ ] 每条题目使用稳定 ID，包含 category、title、text、tags。
- [ ] 题目正文长度不超过真人裁判问题接口的 3000 字限制。
- [ ] 新增只读 GET /api/question-bank，支持 category、q、limit。
- [ ] 接口要求登录；不新增写入 API 和数据库表。
- [ ] 不复用已返回 410 的 /api/rooms/{room_id}/suggestions。

## 最终审查重点

1. 是否存在任何绕过 /api/join 现有准入规则的新路径；旧邀请码是否仍保留 `allow_frozen=True`、提前幂等返回和退赛重入条件。
2. 共享加入核心是否只抽取共同行为，来源特有资格检查是否独立；邀请 / 公开路径是否明确阻止人设冻结时新增参赛者。
3. 重新邀请是否会在创建事务内先过期旧 pending，释放唯一索引。
4. “去大厅查看”是否通过 `leaveCurrentRoom()` 并完整呈现普通成员退房 / 房主关房 / 取消留房的后果。
5. 账号 socket 是否真正与私信面板状态解耦，是否能在重连时补拉邀请，是否只在对应私信会话可见时标记已读。
6. 邀请接受与开赛、关房、满员、角色冲突并发时是否保持事务一致。
7. 公开列表是否通过字段白名单严格避免泄露邀请码、UID、模型配置和比赛内部内容。
8. 公开房间是否只在名单确实可变更时出现，而不是只检查 status='open'。
9. 题库内容是否只作为可编辑草稿，不会自动提交或混入 AI / 外部裁判原文转录。
10. 新增迁移是否可重复执行，且不会改变旧房间默认私密状态。
11. Dockerfile 是否复制 `question_bank.py`，构建容器内是否成功导入并启动题库接口。
