# 图灵实验室 v1.9 使用指南

本文对应 v1.9 代码，涵盖公共聊天、独立裁判管理、个人中心、好友私信和账号积分。本文是当前版本的主要使用入口；实际生产版本以 Railway 已部署的提交为准。历史升级记录保留在仓库的 `UPGRADE_*.md` 文件中；历史文档中的旧界面步骤不应代替本指南。

## 1. 账号注册与登录

1. 打开网站，选择“注册账号”，填写用户名和密码。注册不需要邀请码；名字长度为 1～40 个字符，允许重名，密码至少 8 位。
2. 注册成功后，平台自动分配唯一 UID，例如 `TL00000001`。在大厅复制并保存 UID。
3. 日常使用 UID 和密码登录。升级前创建的旧账号如果暂时不知道 UID，可在登录页选择“使用旧登录名”登录，进入大厅后查看 UID。
4. UID 由账号主键生成，已分配的 UID 永不重用。删除账号不会把旧 UID 分配给新账号。

**用户名或显示名字都不能代替 UID 作为账号身份。请保存 UID。**

## 2. 创建房间与加入身份

### 创建房间

- 登录后进入比赛大厅，使用“创建一场图灵测试”填写比赛名称并创建房间。
- 创建者成为该房间的房主，可以管理参赛者、真人裁判、AI 席位、比赛轮次和最终揭晓。
- 房主可复制房间邀请码，发给需要加入的玩家或裁判。全站管理员可以管理所有房间。

### 以参赛者身份加入

1. 先注册账号并使用 UID 登录。
2. 在大厅“加入已有房间”区域输入房主提供的邀请码。
3. “加入身份”选择“参赛者”，点击“加入比赛”。

### 以真人裁判身份加入

1. 真人裁判自行注册账号，不需要房主代建账号。
2. 使用自己的 UID 和密码登录。
3. 在大厅输入目标房间的邀请码。
4. 在“加入身份”中选择 **“真人裁判”**，然后加入比赛。

真人裁判限制：

- 同一个账号同一时间只能担任一个**未完赛房间**的真人裁判。若账号已在其他未完赛房间担任裁判，必须先完成那场比赛，才能加入另一场。
- 房主不能同时担任自己房间的独立真人裁判；本房间参赛者也不能同时担任本房间裁判。
- 全站管理员账号不能作为独立真人裁判加入。
- 已完赛房间会保留裁判名单。若该房间再次开赛时，某位保留裁判仍在其他未完赛房间担任裁判，系统会阻止再次开赛；先完成其他房间的比赛，再重新开赛。

## 3. 比赛流程

### 独立真人 / AI 裁判出题与统一作答

1. 至少准备两名在场参赛者（真人或 AI）。真人裁判使用自己的账号进入房间，在独立裁判界面提交本轮问题；手动转录的 AI 裁判由房主在“AI 裁判管理”代录问题。
2. 房主在参赛者管理查看本轮状态；真人裁判和 AI 裁判分别在各自管理页面维护。
3. 房主先查看“本轮准备”区：有效参赛者至少 2 人，当前轮至少有一份裁判问题，问题合计不超过 6000 字。若有可用且尚未交题的模型 AI 裁判，可选择 **“生成问题并开始”**；系统只补当前缺失席位，生成后重新检查服务器状态，再开启本轮。若已有合规问题，也可选择 **“按已提交问题开始”**，未交题的真人 / 手动 AI 裁判不会阻止房主按现有规则开局。两个操作都会在开局后触发模型 AI 参赛者回答。

模型 AI 裁判自动出题要求房间仍开放、当前轮处于待出题阶段、至少两名在场参赛者，并且对应 AI 裁判席绑定了可用的个人模型配置。连接测试成功只说明独立测试请求成功，不会替代这些比赛前置条件。批量出题按席位分别记录：已成功保存的问题不会因其他席位失败而回滚；失败或被额度阻止的席位可单独重试。已有问题、手动补录问题和模型问题共同遵守 6000 字上限。
4. 所有参赛者（包括 AI）提交回答后，服务器会统一公开本轮回答。
5. 若要继续比赛，房主在参赛者管理点击“开启下一轮”；新一轮的模型 AI 裁判出题仍按席位记录。失败席位可在 AI 裁判管理页单独重试，不会重复生成已经提交的问题。
6. 全部轮次完成后，各真人裁判分别提交自己的最终判断；房主在“AI 裁判管理”代录手动 AI 裁判判断，或点击“让模型自动完成最终判断”。裁判之间不能查看彼此尚未公开的判断。
7. 所有独立裁判锁定判断且所有轮次回答公开后，房主在参赛者管理点击“全部裁判已锁定 · 正式揭晓”。

**自动调用不是服务器独立运行的后台任务。** “开始统一作答”由当前浏览器按顺序发起请求；如果页面、网络或某一步请求中断，后续步骤可能没有触发。相关管理页面保留了补触发入口。

### 手动发布问题与 AI 回答

参赛者管理还保留“向所有玩家发布问题”的入口。它仅适用于没有启用真人或 AI 独立裁判的房间，且本轮仍处于待发布状态。它用于房主录入外部裁判的问题并发布给玩家，**不会自动生成模型 AI 参赛者的回答**；启用了独立裁判的房间应使用上面的统一作答流程。

使用这条路径时：

- 对绑定可用模型配置、但尚未回答的 AI 参赛者，房主需要另外点击 **“自动生成模型 AI 回复”**。
- 未绑定模型 API 或配置暂不可用的 AI 参赛者，需要房主通过“录入 AI 回答”表单粘贴原始回答。
- 如果模型 AI 回答生成失败或中断，只要存在绑定有效模型配置、尚未提交回答的席位，且当前轮仍在收集回答，参赛者管理就会显示补触发按钮，可再次点击。
- 在没有独立裁判的手动流程中，全部轮次回答公开后，房主代录外部裁判的最终判断，锁定后点击“揭晓身份与计分”。

独立裁判流程的补触发入口位于“AI 裁判管理”：当前轮尚未开启且有可用模型 AI 裁判未交题时，可点击 **“让模型自动生成本轮问题”**；最终判断在全部轮次完成后另行触发。

## 4. 房间公共聊天与裁判管理

### 公共聊天

- “比赛现场”中的“公共聊天”按**场次**保存，不随所选轮次切换。
- 可见及可发言的身份仅包括：本房间在场的人类参赛者、房主和全站管理员。未加入房间的人、已被移除的成员和真人裁判不能读取或发送。
- 真人裁判及 AI 裁判看不到公共聊天。聊天正文也不会进入 AI 提示词、匿名资料、裁判快照、比赛 Log 或通用事件日志。
- 本期只支持纯文本，单条消息最多 2000 字符；发送时会去除首尾空白，空消息会被拒绝。消息显示发送者名字、UID 和时间；允许重名，UID 用于区分身份。
- 聊天通过房间 WebSocket 实时同步；刷新或断线重连后可恢复当前场次消息。不同房间互相隔离。

**完赛清除规则：** 房主成功执行正式揭晓（独立裁判流程为“全部裁判已锁定 · 正式揭晓”，外部裁判流程为“揭晓身份与计分”）、服务器将房间标记为完赛时，会在同一数据库事务中删除本场聊天。裁判刚锁定判断、某一轮回答公开都不算正式完赛。完赛后聊天输入关闭，刷新和重连不能恢复旧正文；再次开赛使用新的空聊天区。比赛问题、回答、裁判判断、快照和 Log 不会因清聊而删除。

### 真人裁判管理与 AI 裁判管理

房间导航将两类裁判管理分开：

- **真人裁判管理**：集中查看真人裁判名单、UID 和锁定状态；真人裁判仍自行注册、UID 登录、通过邀请码选择“真人裁判”加入。房主不创建裁判账号，也不绑定已有账号。
- **AI 裁判管理**：添加 AI 裁判席位、选择个人模型配置、手动录入问题、自动生成问题、手动录入最终判断或触发模型最终判断。
- **参赛者管理**：保留“开始统一作答”、多裁判锁定进度和最终揭晓入口。纯真人、纯 AI 或混合裁判房间都从同一套比赛状态流程开局和揭晓。

## 5. 个人中心与模型 API

所有登录用户（普通用户、真人裁判、房主和全站管理员）都可以从大厅或房间进入“个人中心”，不需要先创建或加入房间。

### 基本资料与密码

- UID 只读且可复制；名字可修改，允许重名。保存后当前 `username` 与 `display_name` 会同步为同一个新名字；UID、房间归属和历史快照中的固定署名不变。
- 旧账号原有的 `legacy_username` 独立保留，仍可通过“使用旧登录名”登录；修改当前名字不会迁移、覆盖或删除旧登录名。
- 修改密码需要输入当前密码、新密码和确认密码。新密码长度为 8～200 字符。
- 密码修改成功后，该账号的所有登录会话（包括当前会话）都会失效，需要使用新密码重新登录。管理员原有的重置他人密码权限不变。

### 个人模型 API 配置

模型 API 使用 OpenAI Chat Completions 兼容协议。**配置在个人中心创建、编辑、测试和删除**，不再在房间中创建或编辑模型配置。

已有配置默认收起。点击配置名称即可独立展开该配置的模型标识、Base URL、凭据状态、编辑表单、测试连接和删除操作；同名配置也按各自配置 ID 独立折叠。收起和展开不会丢失尚未保存的输入。

配置状态“API Key 已保存（可解密）”只表示服务器能够解密已保存凭据，不代表服务商连接或 AI 出题成功。请在展开配置后点击“测试连接”；最近一次测试结果会单独显示。编辑配置字段后，旧测试结果会清除。

常用配置字段：

| 字段 | 说明 |
|---|---|
| 配置名称 | 便于区分服务商或用途 |
| Base URL | OpenAI 兼容 API 根地址，例如 `https://api.openai.com/v1`；不要附加 `/chat/completions` |
| 模型名称 | 服务商提供的模型 ID |
| API Key | 对应服务商的密钥 |
| 采样温度 | 0～2，默认 0.7，步长 0.1 |
| 最大输出 Token | 64～8192，默认 2048 |
| 请求超时 | 10～120 秒，默认 60 |

- 个人配置归创建者所有，可在其有权管理的多个房间中复用。配置列表、编辑、删除和独立测试仅限本人；全站管理员也不会自动获得读取他人个人配置的权限。
- 在房间添加 AI 参赛者或 AI 裁判时，房间管理者可选择“手动转录”或**自己拥有**的可用个人配置。选择配置不会把密钥复制给其他成员。
- 管理其他用户房间的全站管理员，可以使用自己的个人配置绑定 AI 席位。房间内已有经授权的他人配置绑定可以继续使用；房间管理者只能看到该席位必要的安全摘要，不能列举或编辑配置拥有者的其他配置。
- 绑定意味着该房间的房主和全站管理员可通过比赛操作触发此配置的模型调用。服务商可能按实际调用量计费，请确认配置拥有者已授权。比赛生成请求取得并发额度后，会在实际访问服务商前重新检查登录会话、权限、配置所有者与凭据状态、席位绑定和比赛上下文；已失效的排队请求不会发往服务商。已经发出的请求仍可能产生费用。
- 房间删除、清空比赛记录或再次开赛都不会删除个人模型配置。删除个人配置会解除所有引用该配置的 AI 席位绑定，席位、匿名代号、答案和判决历史仍保留。删除账号后，该账号的个人配置不会再发起新调用，房间比赛历史仍保留。
- 有效的已保存 API Key 在编辑时留空表示保持原值；密钥缺失或密文损坏时必须重新录入服务商 API Key 才能修复。
- API Key 在服务器端使用 Fernet 加密后写入 SQLite；浏览器只会收到配置元数据和凭据状态，不会收到原 API Key 或密文。
- 当前模型 API 仅允许 HTTPS 公网地址。模型服务商的 API 用量可能单独计费。
- **妥善备份并长期固定 `MODEL_CREDENTIAL_KEY`。** 启动时会逐条检查已保存凭据，包括空密文。密钥不可用时，页面只显示“模型 API 暂不可用，请联系管理员。”网站仍可使用手动转录；密钥恢复和损坏配置的修复步骤见 [Railway 部署说明](RAILWAY_部署说明.md) 第 5.3 节。


### 模型调用记录与用量

个人中心的“个人模型 API”区域下方提供可折叠的“模型调用记录”，仅显示当前账号拥有的模型配置所产生的调用，包括本人连接测试，以及房间管理者 / 全站管理员触发的比赛调用。

每条记录显示：

- 调用时间、配置名称与模型名称快照、用途。
- 房间、场次、轮次（适用时），以及配置所有者和实际触发者。
- 排队等待时间、实际请求耗时、输入 / 输出 / 总 Token。
- 任务状态、服务商请求是否成功、结果是否写入比赛，以及安全的失败原因。

记录支持按模型配置、用途和状态筛选，并分页查看。统计范围是**当前保留记录**，不是服务商全历史账单。服务商未返回 usage 时显示“未返回”，不补成 0；只对有已知用量的记录汇总 Token。平台不估算价格，不实现账单或充值。

调用记录不会保存 API Key、密文、认证头、完整请求 / 响应正文、提示词、公共聊天或未公开判决。全站管理员不会因为管理员身份而获得其他账号的个人调用列表。

保留与清理规则：

- 比赛完赛本身不清除调用明细；查看或下载比赛 Log 不影响记录。
- 清空完赛记录、再次开赛或删除房间时，对应旧场次的调用明细和按场用量一并清理。
- 删除模型配置只清除该配置的独立连接测试记录；已经发生的比赛调用记录保留到所属比赛记录清理。
- 账号删除后，记录仍按原配置所有者归属，不会变成公开记录。

### 模型任务状态与失败恢复

参赛者管理和 AI 裁判管理页按目标席位显示模型任务。状态含义：

| 状态 | 含义 |
|---|---|
| 排队中 | 任务已接受，等待全局模型并发槽 |
| 请求中 | 已通过最终预检并进入服务商请求阶段 |
| 已完成 | 内容已通过检查并成功写入比赛；连接测试则表示测试完成 |
| 失败 | 请求或返回内容处理失败 |
| 已阻止 | 权限、比赛状态、配置或本场请求上限阻止了操作；未必已发出服务商请求 |
| 已作废 | 等待或生成期间上下文变化，结果不能写入当前比赛 |
| 已中断 | 服务重启后无法确认请求是否完成，需要核对比赛内容后手动恢复 |

批量生成会拆成独立席位任务。一个席位失败不会撤销其他席位的成功结果。失败、中断或因额度被阻止的任务，在目标仍然缺失、配置和比赛上下文仍匹配时可使用 **“重试此席位”**。重试只请求指定席位，不覆盖已经提交的问题、回答或已锁定判断；旧失败记录保留，新重试会生成新的调用记录。

服务重启后不会自动重发可能已经计费的请求。系统先核对任务所属场次、轮次和目标内容，再将无法继续的任务标为“已中断”或“已作废”。请求成功但结果因比赛变化被丢弃时，会分别显示“请求成功”和“结果未应用”。

### 本场模型请求次数上限

房主和全站管理员可以在参赛者管理“本轮准备”区设置本场模型请求上限：

- 新房间和升级后的既有房间默认 **不限**；留空保存为不限。
- 上限必须为正整数。达到上限后，新的比赛模型请求会被服务端阻止；可提高上限或使用手动转录。
- 每个实际进入服务商请求阶段的目标席位计 1 次。一次批量操作若有 3 个席位实际开始请求，就计 3 次；单席重试再计 1 次。
- DNS / 连接失败、超时、空响应、解析失败和结果作废，只要已经进入请求阶段，仍计入本场次数。排队期间被作废、最终权限检查未通过或额度不足而未开始请求的任务不计入。
- 独立连接测试不计入本场上限。
- 上限调低到已用次数以下不会撤销既有结果，只会阻止后续新请求。换绑、删除配置或刷新页面都不会清零本场次数。
- 再次开赛保留上限设置，新场次的计数从 0 开始。

这是平台侧的**请求尝试次数控制**，不代表服务商账户的货币消费上限。超时或结果作废的请求仍可能产生服务商费用。

### 旧接口兼容说明

- 旧版房间模型 API 的创建、修改、删除和测试入口保留为受控兼容适配层；它们不再创建房间所有的配置，而是以当前登录用户为配置所有者。调用者必须同时具备房间管理权限和该个人配置所有权。
- 房间状态不会列出某位用户的全部个人配置；管理者只会收到当前 AI 席位已绑定配置的必要安全摘要。个人配置列表统一通过个人中心使用。
- AI 席位的新增与换绑都由服务器验证“房间管理权限 + 当前用户拥有该配置”。保留原有他人配置绑定不等于授予其配置列表、密钥、编辑或独立测试权限。
- 旧的 `POST /api/rooms/{room_id}/suggestions` 写入口已停用，返回 HTTP 410。历史 `suggestions` 记录保留原样，不会被转换为公共聊天；正式题目和回答仍走原来的独立接口。

## 6. 房间复用、记录与 UID

- 比赛完成后，房主可以使用“再次开赛”复用房间。房间、邀请码和保留名单继续使用，上一场的比赛问题、回答、裁判判断、日志和快照会被清空。
- 再次开赛前，系统会检查保留的真人裁判是否仍在其他未完赛房间任职；存在冲突时会拒绝开赛，不会先清空上一场记录。
- 比赛结束后可下载整场 Log。需要保留历史记录时，请先下载并妥善保存。
- 删除房间会永久删除该房间及其比赛数据；这与“清空完赛记录后复用房间”不是同一操作。个人模型配置不随房间删除。

## 7. 本地测试与 CI

在项目根目录使用 Python 3.13、Node.js 20 或更新版本（CI 使用 Node.js 22），先安装 Python 测试依赖：`python -m pip install -r requirements-dev.txt`。

项目的浏览器验收测试包括 `tests/test_uid_ui.py` 和 `tests/test_host_ui.py`（后者同时运行参赛者管理和房间删除浏览器脚本）；`tests/test_uid_ui.py` 会运行 UID、个人模型配置、出题入口、模型调用管理，以及 `tests/social_points_ui.cjs` 中的好友申请、私信、名字锁定和账号积分浏览器验收。它们都会启动 Playwright 浏览器。

无 Microsoft Edge、也不准备运行浏览器验收时，运行后端测试应同时排除这两个文件：

python -m pytest -q --ignore=tests/test_uid_ui.py --ignore=tests/test_host_ui.py

本机安装 Playwright Chromium 后，可在 PowerShell 中运行完整测试：

```powershell
npm install --no-save playwright
npx playwright install chromium
$env:PLAYWRIGHT_CHANNEL = "default"
python -m pytest -q
```

新增后端覆盖：`tests/test_match_readiness.py`、`tests/test_model_operations.py`、`tests/test_name_lock.py`、`tests/test_social_points.py`；`tests/test_points.py` 覆盖积分计算和已移除参赛者的历史判断兼容。浏览器覆盖：`tests/model_operations_ui.cjs`、`tests/social_points_ui.cjs`，均由 `tests/test_uid_ui.py` 接入 pytest。GitHub Actions 的 `.github/workflows/tests.yml` 安装 Chromium，并设置 `PLAYWRIGHT_CHANNEL=default` 后执行完整的 `python -m pytest -q`；CI 不依赖 Microsoft Edge。

## 好友、私信与账号积分

### 好友关系

- 在个人中心输入完整 UID 搜索账号；比赛现场的真人参赛者名单也提供快捷添加入口。UID 是唯一身份标识，显示名字允许重复。
- 好友申请由接收方接受或拒绝；发送方可撤回。已拒绝或已撤回的申请可以重新发送。双方同时申请时，服务端会提示接受对方已有的申请。
- 好友备注只保存在设置者自己的账号下，不会覆盖对方的显示名字；可随时恢复为对方当前名字。
- 删除好友会立即解除双方发送新私信的权限，但保留历史会话。之后重新成为好友时会继续使用原会话，不会复制历史消息。

### 一对一私信

- 仅当前好友可以发送纯文本私信，单条最多 2000 字；不支持图片、文件、语音、在线状态或已读回执。
- 会话按 UID 隔离，支持历史分页、未读计数、离线后重新加载和账号级 WebSocket 实时推送。多标签页按服务器消息 ID 去重。
- 客户端为每次发送生成请求标识；网络超时后重试会复用同一标识，服务端保证同一账号的同一请求标识只产生一条消息。
- 删除好友后仍可查看既有会话，但不能发送新消息。账号被删除后，好友关系和待处理申请会失效；保留的会话历史可由另一方查看，删除账号不能再收发消息。
- 账号级 WebSocket 会在每次推送时重新验证会话。退出登录只撤销当前登录会话；修改密码、管理员重置密码或删除账号会撤销该账号的全部会话。
- 私信只对会话双方开放，不会进入房间公共聊天、匿名裁判包、比赛 Log、模型提示词或管理员通用用户管理界面。

### 账号积分

- 只有正式揭晓时仍在场、账号未删除的人类参赛者参与积分结算；AI 席位、房主旁观身份、裁判身份和已退赛 / 已移除参赛者不计分。
- 每名有效人类参赛者独立统计全部有效裁判的判断。严格多数裁判将其判为 AI 才算胜利；平票按失败处理。
- 胜场基础分为 10 分。当前连续胜场数为第 (n) 场时，奖励为 `ROUND_HALF_UP(10 × 1.2^(n-1))`；失败扣 10 分并将连胜清零。总积分最低为 -100，触底时实际扣分为剩余差额，积分不再下降，但连胜仍会清零。
- 结算使用整数运算，积分和连胜以十进制字符串持久化；每个房间场次有唯一结算标记。重复揭晓、刷新、清空比赛记录、再次开赛或删除房间都不会重复结算或回退历史积分。
- 个人中心显示总积分、当前连胜和可分页的积分流水；好友搜索结果及好友列表也显示公开的总积分和连胜。比赛结束页只显示当前账号自己的本场结果、实际积分变化及更新后的积分。

### 比赛期间名字锁定

- 第一次成功开始统一作答后，服务器记录本场开始时间。只要比赛仍未正式揭晓，房主、真人裁判和本场参赛者不能修改账号名字；退出页面、退出登录或被移出参赛名单都不会解除本场锁名。
- 名字锁定按账号在所有未完赛房间中的身份统一判断。只要账号在任一场未完赛且已开局的比赛中担任房主、真人裁判或参赛者，就不能修改名字。
- 仅以管理员身份旁观、没有担任房主 / 真人裁判 / 参赛者的账号不锁名。比赛正式完赛或房间删除后，相关身份不再锁名。
- 个人中心根据服务器返回的状态禁用名字输入框；保存接口会在数据库写事务中再次检查，开局与改名并发时只会出现“改名先完成”或“开局先锁定”两种一致结果。
